# 产品详情页推荐产品下移可行性研究

## 1. 研究目标

目标页面：
- `https://www.zgzonre.com/archives/399`

本次先聚焦第一个运营反馈问题：
- 当前“推荐产品/最新文章”位于正文右侧。
- 业务期望：将该模块移动到正文下方。
- 本次只兼容 PC 页面，不考虑移动端场景。

本研究只讨论这个问题的可行性、实现边界、风险与推荐方案，不直接处理其他详情页问题。

## 1.1 当前确认的业务目标

详情页重构后的目标结构，当前已明确为：

1. 最上方显示标题
- 标题上方增加一个返回按钮
- 按钮用于返回上一级页面
- 适用于页面实际嵌入 WordPress 后，从列表页或分类页进入详情页的场景
- 使用 `title.rendered`

2. 标题下方显示分类信息
- 展示格式：`分类：二级分类 / 一级分类`
- 如果当前文章只有一级分类，则只显示一级分类
- 如果同时存在一级和二级分类，优先显示二级分类，再显示所属一级分类

3. 正文区域保持富文本渲染
- 正文仍然使用当前文章详情 HTML
- 正文详情区域在 PC 端使用固定内容宽度，不做 `100%` 通栏
- 建议正文版心宽度控制在 `900px - 960px`
- 正文容器整体居中，保证阅读密度稳定

4. 正文下方增加“推荐产品”
- 推荐产品区是独立模块，不属于正文富文本
- 每项显示：图片、标题、链接
- 推荐数量固定为 `6`
- 推荐逻辑为同类产品推荐
- 当前先按随机推荐整理方案，但推荐源必须限定在当前产品所属主分类内

5. 路由方案
- 原页面链接仍然保留，例如：`https://www.zgzonre.com/archives/1071`
- 新重构页允许按参数路由显示，例如：`?article_id=1071`
- 后续可通过一个统一详情页模板，按 `article_id` 动态拉取详情并渲染

## 2. 当前页面结构结论

通过线上页面结构分析，当前详情页主体是典型的两栏布局：

1. 左侧主内容区，约 `70%`
- 标题
- 作者/分类/发布时间
- 正文详情
- 标签
- 上一篇/下一篇导航

2. 右侧侧栏区，约 `30%`
- 标题：`最新文章`
- 一个 `wp-block-query` 列表
- 列表项包含缩略图、标题、分类、日期

也就是说，当前“推荐产品”并不是正文里的独立区块，而是作为右侧 sidebar 存在。

## 3. 线上页面现状判断

### 3.1 当前模块的真实语义

当前右侧模块标题是：
- `最新文章`

当前数据来源是：
- WordPress Query Block（`wp-block-query`）

当前列表逻辑从页面结构看，更接近：
- 全站最新文章

而不是：
- 当前产品详情的相关推荐
- 同分类推荐产品
- 同标签推荐产品

所以运营说“推荐产品放在下面”，其实包含两层含义：

1. 位置问题
- 模块现在在右侧，影响正文阅读连续性。

2. 语义问题
- 当前模块标题与查询逻辑是“最新文章”，不完全等于“推荐产品”。

### 3.1.1 当前确认的推荐语义

业务已进一步确认：
- 推荐区不是全站随机文章
- 也不是严格只看当前二级分类
- 当前采用“同类产品推荐”

当前定义为：
- 如果当前详情页属于加热器体系，则推荐区展示加热器同类产品
- 如果当前详情页属于搅拌设备体系，则推荐区展示搅拌设备同类产品
- 如果当前详情页属于水处理体系，则推荐区展示水处理同类产品

这意味着：
- 打开同一主分类下的不同详情页时，推荐区来源都限定在该主分类范围内
- 推荐结果可以随机，但随机池不能跨主分类

### 3.2 当前详情页可直接使用 WP 标准接口

当前详情页不需要额外找专用接口，已确认可直接使用 WordPress REST API。

详情接口示例：

```http
GET https://www.zgzonre.com/wp-json/wp/v2/posts/399
```

已确认可返回的关键字段包括：
- `id`
- `link`
- `title.rendered`
- `content.rendered`
- `excerpt.rendered`
- `featured_media`
- `categories`

以 `https://www.zgzonre.com/archives/399` 为例，实际返回要点：
- `id = 399`
- `link = https://www.zgzonre.com/archives/399`
- `title.rendered = 旋流除污器`
- `featured_media = 398`
- `categories = [39, 50]`

这意味着后续如果要做前端化详情页或“正文下方推荐产品”，可以直接基于详情接口拿到：
- 当前文章 ID
- 当前文章所属分类
- 当前文章正文 HTML
- 当前标题与分类基础数据

进一步建议：

1. 详情接口

```http
GET /wp-json/wp/v2/posts/{id}
```

2. 推荐列表接口

```http
GET /wp-json/wp/v2/posts?categories={CATEGORY_ID}&exclude={CURRENT_ID}&per_page=6
```

例如当前页可用：

```http
GET /wp-json/wp/v2/posts?categories=50&exclude=399&per_page=6
```

3. 如果前端需要一次拿到封面图等嵌套信息，建议使用：

```http
GET /wp-json/wp/v2/posts/{id}?_embed=1
```

结论：
- 详情页重构具备现成接口基础。
- “推荐产品下移”如果后续升级成真正的动态推荐，不会缺少详情数据来源。

### 3.2.1 顶部分类渲染建议

如果顶部需要显示：

```text
分类：二级分类 / 一级分类
```

建议使用两种方式之一：

1. 详情接口 `?_embed=1`
- 通过 `_embedded.wp:term` 读取当前文章分类
- 再根据分类的 `parent` 字段区分一级/二级

2. 详情接口 + 分类接口
- 先通过 `/wp-json/wp/v2/posts/{id}` 拿到 `categories`
- 再请求 `/wp-json/wp/v2/categories?include={ids}`
- 根据 `parent=0` 和 `parent!=0` 组装显示顺序

当前推荐：
- 优先使用“详情接口 + 分类接口”方式

原因：
- 分类层级判断更直接
- 结构更清晰
- 更便于后续做一级/二级分类兼容

### 3.3 当前正文内容是富文本 HTML

已确认当前详情正文不是纯文本，而是 WordPress 返回的富文本 HTML。

依据：
- 详情接口返回的是 `content.rendered`
- 页面源码正文区域包含：
  - `<div class="artview_detail goods-info desckey0">`
  - `<p>`
  - `<span>`
  - `<strong>`
  - `<br>`
  - `<img>`
  - 各类内联样式（如 `font-size`、`line-height`、`font-family`）

这意味着后续如果做前端化详情页，正文不能按纯文本处理，而必须按富文本容器渲染。

### 3.4 富文本渲染约束

如果后续详情页改为接口驱动，正文建议遵循以下约束：

1. 保留富文本结构
- 正文使用 `content.rendered` 渲染。
- 不要转纯文本，否则段落、图片、加粗、换行都会丢失。

2. 只在专用正文容器中渲染
- 例如 `.entry-content` 或独立的详情容器。
- 避免富文本样式污染推荐区、导航区和外层页面布局。
- 正文容器宽度在 PC 端固定，不使用 `width: 100%` 通栏铺满。

3. 重点约束图片
- `img { max-width: 100%; height: auto; }`
- 避免原文图片把版心撑坏或超出容器。

4. 推荐区必须和正文区分离
- 推荐产品模块不能混入富文本正文内部。
- 应作为正文后的独立 section 输出。

## 4. 可行性分析

## 4.0 重构后的目标布局

当前建议的 PC 详情页结构如下：

1. 顶部标题区
- 返回按钮
- 标题
- 分类信息（`分类：二级分类 / 一级分类`）

2. 正文富文本区
- 直接渲染当前文章正文 HTML
- 使用固定版心宽度，建议 `900px - 960px`
- 不使用 `100%` 宽度横向铺满页面
- 正文区域居中，优先保证阅读体验而不是占满空间

3. 推荐产品区
- 标题建议：`推荐产品`
- 位于正文之后
- 与正文明显分区
- 推荐区可使用比正文更宽的容器
- 推荐区建议使用独立 PC 版心，例如 `1200px`

4. 文章导航
- 上一篇/下一篇可放在推荐区之后
- 或保留在正文与推荐区之间，后续根据视觉稿决定

### 4.0.1 返回按钮要求

详情页顶部增加一个独立返回按钮，位置建议：
- 位于标题区最上方
- 在标题之前显示
- 作为单独一行按钮，不与标题挤在同一行

交互建议：

1. 优先返回上一级页面
- 使用浏览器历史记录返回
- 即优先执行 `history.back()`

2. 兜底逻辑
- 如果用户是直接打开详情页，没有有效历史记录，则跳转到预设列表页
- 建议兜底地址后续可配置，例如：
  - 产品总列表页
  - 当前主分类列表页
  - 统一产品页

3. 按钮文案
- 建议使用：`返回上一页`
- 也可用：`返回列表`

视觉建议：

1. 使用单独按钮样式
- 不要做成纯文本链接
- 需要具备明显可点击感

2. 样式方向
- 简洁、轻量、偏业务型
- 可配合左箭头图标
- 建议中小尺寸，避免压过标题本身

3. PC 端排版
- 按钮与标题区之间保留明确间距
- 不与分类信息混排

## 4.1 方案 A：只调整位置，不改数据逻辑

### 方案说明

保留现有右侧 `wp-block-query` 模块和数据源不变，仅把布局从：
- 左正文 + 右侧栏

改成：
- 上方正文
- 下方推荐模块

### 可行性

可行，而且风险最低。

原因：
- 当前 DOM 顺序本来就是“左列在前，右列在后”。
- 右侧“最新文章”模块已经是独立块，不需要先拆数据。
- 可以通过区块布局调整或 CSS 控制，把右栏改成下沉到底部。

### 实现路径

有两种做法：

1. 模板/区块编辑方式
- 把 `wp-block-columns` 两栏结构改成单栏结构。
- 将右栏 query block 整体下移到正文区块之后。

2. CSS 方式
- 保持现有两栏 DOM 不变。
- 在桌面端把右列设置为 `flex-basis: 100%`，并换行到下一行。
- 左侧正文扩展为 `100%` 宽度。

### 优点

- 改造快。
- 风险低。
- 不需要动文章数据。
- 不需要新增接口。

### 缺点

- 只是把“最新文章”挪到下面。
- 业务语义仍然不是严格的“推荐产品”。

### 适用场景

适合第一阶段快速上线。

如果当前运营最核心诉求是：
- “不要占右侧阅读空间”
- “让正文先完整看完”

那么此方案足够成立。

## 4.2 方案 B：位置下移 + 模块语义改成“推荐产品”

### 方案说明

不仅把模块放到正文下方，还把它从“最新文章”调整为真正的“推荐产品”。

例如改成：
- 同分类推荐
- 同主分类下其他产品
- 当前产品所属分类优先推荐

### 可行性

可行，但不再是单纯样式改动。

它会涉及：
- WordPress 模板区块调整
- Query Block 查询条件调整
- 或者额外的前端/后端推荐逻辑

### 实现路径

1. 纯 WP 区块配置
- 如果当前模板支持按分类过滤 Query Block，可将其改为当前分类相关文章。
- 再把标题改为“推荐产品”。

2. 模板定制
- 针对 `single post` 模板做定制推荐区。
- 通过当前文章分类/标签生成推荐内容。

3. 前端异步推荐区
- 页面正文后插入一个自定义推荐模块。
- 通过 REST API 拉当前分类相关文章。

### 优点

- 业务语义更准确。
- 推荐质量更高。
- 更符合“产品详情页”的转化目标。

### 缺点

- 改造范围更大。
- 需要明确推荐规则。
- 测试成本高于单纯挪位置。

### 适用场景

适合第二阶段优化。

如果业务目标不只是阅读体验，而是：
- 提升详情页继续点击率
- 提升产品链路转化

那这个方案更值得做。

### 4.2.1 推荐数据来源建议

如果第二阶段把“最新文章”升级为真正的“推荐产品”，建议优先使用现有 WP REST API，而不是第一阶段就单独写 PHP 推荐文件。

推荐原因：
- 当前详情接口已经能拿到文章 `id`、`categories`、`featured_media`、`content.rendered`
- 推荐列表可以直接按当前分类或主分类查询
- 不需要新增后端接口，维护成本更低

建议接口模式：

1. 当前详情

```http
GET /wp-json/wp/v2/posts/{id}?_embed=1
```

2. 同分类推荐

```http
GET /wp-json/wp/v2/posts?categories={CATEGORY_ID}&exclude={CURRENT_ID}&per_page=6&_embed=1
```

如果当前业务以“同主分类推荐”为准，则建议直接按主分类聚合查询。

例如：
- 当前文章属于“加热器系列产品”主分类
- 那么推荐池来自整个加热器主分类体系，而不是只来自某一个二级分类

实现上建议：

1. 先识别当前文章所属主分类
- 例如加热器 / 搅拌设备 / 水处理设备

2. 根据主分类映射出推荐分类集合

示例：
- 加热器：`42,43,44,45,46`
- 搅拌设备：`47,48`
- 水处理设备：`49,50,51,67`

3. 再查询该主分类下文章

```http
GET /wp-json/wp/v2/posts?categories=42,43,44,45,46&exclude={CURRENT_ID}&per_page=12&_embed=1
```

如果需要“随机推荐 6 个”，建议不要直接依赖后端随机排序，而是采用前端可控方案：

1. 先按当前主分类取一批候选数据

```http
GET /wp-json/wp/v2/posts?categories={CATEGORY_IDS}&exclude={CURRENT_ID}&per_page=12&_embed=1
```

2. 前端对候选列表做随机打散

3. 最终取前 `6` 条作为推荐产品

这样做的原因：
- WordPress 标准 REST 接口默认不稳定支持真正的随机排序
- 前端打散更可控
- 仍然可以保证推荐来源和当前产品同类

当前推荐规则建议固定为：

1. 先识别当前文章所属主分类
2. 推荐池限定在当前主分类内
3. 始终排除当前文章
4. 对候选池随机打散
5. 最终输出 6 条

### 4.2.1.1 推荐产品展示字段

推荐产品区每个卡片只显示以下三项：

1. 图片
- 使用文章封面图
- 建议通过 `_embed` 直接读取

2. 标题
- 使用 `title.rendered`

3. 链接
- 使用文章 `link`

当前阶段不建议在推荐卡片中显示：
- 摘要
- 分类串
- 发布时间

原因：
- 当前业务要求是“图片 + 标题链接”
- 卡片需要尽量紧凑，适合一次展示 6 个

### 4.2.1.2 推荐产品区 PC 排布建议

因为当前只兼容 PC，不考虑移动端，推荐区建议直接按 PC 视觉定稿：

1. 默认展示 6 个卡片
2. 优先做成一行 6 个紧凑卡片
3. 每个卡片只保留图片 + 标题
4. 标题最多两行，超出省略
5. 卡片高度统一，避免上下参差不齐

如果后续视觉评审认为一行 6 个过于拥挤，再退回：
- `3 列 x 2 行`

但当前按照业务方原始要求，建议先以：
- `PC 一屏显示 6 个`

作为默认开发目标

### 4.2.2 当前不建议直接上 PHP 随机推荐算法

第一阶段不建议单独写 PHP 文件做随机推荐，原因如下：

1. 随机推荐不等于相关推荐
- 产品详情页更需要相关性，而不是随机性。
- 纯随机容易把不相关产品推给用户。

2. 当前接口已经足够支撑推荐
- 优先同二级分类
- 数量不足时补同主分类
- 排除当前文章

3. PHP 算法会增加维护点
- 多一套后端推荐逻辑
- 多一套路由/接口维护
- 后期还要处理权重、缓存、排除规则

当前推荐的优先级是：
- 第一阶段：先把模块移到底部
- 第二阶段：优先做“同分类推荐”
- 第三阶段：如业务需要，再考虑更复杂的推荐策略

### 4.2.3 路由建议

当前详情页重构建议支持参数化路由：

1. 原有文章链接继续保留
- 例如：`https://www.zgzonre.com/archives/1071`

2. 新版重构页支持：
- `https://www.zgzonre.com/详情页重构路由?article_id=1071`
- 或者统一页面里通过 `?article_id=1071` 动态渲染

3. 页面初始化逻辑
- 从 URL 读取 `article_id`
- 请求 `/wp-json/wp/v2/posts/{article_id}?_embed=1`
- 渲染标题、分类、正文、推荐产品

这样做的好处：
- 一个模板页可以复用所有产品详情
- 不需要每篇文章单独复制 HTML
- 后续详情页结构调整时只改一份模板

## 5. 风险点

## 5.1 只用 CSS 下移的风险

如果仅用 CSS 把右栏压到下面，需要确认：
- 当前两栏容器在各详情页结构是否一致。
- 主题更新后 class 是否稳定。
- 某些页面如果右栏为空，是否会留下空白容器。

结论：
- 可做，但属于“结构未动、表现层重排”。
- 适合快速验证，不适合作为长期唯一方案。

## 5.2 直接改模板的风险

如果直接改详情页模板，需要确认：
- 所有产品详情页是否共用同一个 single template。
- 非产品类文章是否也走这套模板。
- 改动后是否会影响新闻、AI 页面、招聘页等其他文章页。

结论：
- 改模板前必须先确认模板作用范围。

## 5.3 推荐逻辑的风险

如果要把“最新文章”改为“推荐产品”，必须先定规则：
- 是同二级分类推荐？
- 还是同主分类推荐？
- 是否排除当前文章？
- 推荐几条？
- 是否优先有图文章？

如果规则不先定，开发会反复返工。

## 6. 推荐实施顺序

建议分两步做，不要一步到位混在一起。

### 第一步：先解决位置问题

目标：
- 把右侧 `最新文章` 模块移到正文底部。
- 顶部增加返回按钮
- 顶部明确渲染“标题 + 分类：二级 / 一级”
- 正文后输出独立的“推荐产品”区

建议方式：
- 优先模板/区块调整。
- 如果需要快速验证，可以先用 CSS 做重排验证视觉效果。

交付结果：
- 页面从“两栏阅读”改为“正文优先 + 底部继续阅读”。
- 用户可通过顶部按钮快速返回上一级页面。
- 推荐产品区按 PC 方案展示 6 个卡片。

### 第二步：再决定是否升级为“推荐产品”

目标：
- 把模块从“最新文章”升级为真正的推荐区。

建议先确认：
- 推荐规则
- 数据来源
- 是否全产品详情页共用

## 7. 结论

“推荐产品放在下面”这件事是可行的，而且分层后很清晰：

1. 如果只改位置
- 高可行
- 低风险
- 可以快速上线验证

2. 如果同时改成真正的“推荐产品”
- 也可行
- 但已经从样式问题升级为模板与查询逻辑问题

当前建议：
- 第一阶段先做“下移到底部”
- 同时把顶部分类展示和 `article_id` 路由方案定下来
- 第二阶段再做更复杂的推荐逻辑重构

这样节奏最稳，返工最少。

## 7.1 正文区宽度规则

当前业务已经补充确认：
- 文章内容详情区域不要做 `100%` 宽度
- 正文区应固定内容版心，避免整行过长导致阅读体验发散

当前建议规则：

1. 页面外层可使用较宽 PC 容器
- 例如 `1200px`

2. 正文详情区使用更窄阅读版心
- 建议 `900px - 960px`

3. 推荐产品区可与正文分开控制宽度
- 推荐区可回到较宽的 PC 容器
- 这样既保证正文可读性，也能保证 6 个推荐卡片有足够展示空间

## 8. 当前建议落地方式

建议优先采用：
- `详情页模板重排 + 保留现有 query block`

不建议第一步就做：
- JS 注入一个新的推荐模块

原因：
- 当前推荐列表本身已经存在。
- 先移动现有模块，工作量最小。
- 等业务确认效果后，再决定是否升级为真正的相关推荐。
