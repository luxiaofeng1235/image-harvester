# 业务展示页严格还原重构规范

## 1. 目标

适用于 `网站开发`、`AI平台`、`程序开发`、`App开发` 等业务展示页的重构。

核心目标只有 4 条：

1. 在视觉结构上尽量还原原页面，不随意改布局、尺寸、比例、留白。
2. 设计原则上页面不能出现无意义留白，尤其是底部、尾部不能出现明显空白段。
3. 在代码结构上做干净拆分，去掉旧站冗余脚本和无关依赖，保证后期可维护。
4. 最终产物支持同步到 OSS，并可嵌入 WordPress 页面使用。

---

## 2. 适用范围

本规范适用于以下类型页面：

1. 主要是静态展示页。
2. 原页面存在大量旧建站平台遗留代码、内联脚本、样式冲突风险。
3. 页面本身交互较少，重点是视觉还原，而不是功能开发。
4. 后期需要嵌入到 WordPress 页面中。

不适用于：

1. 分类页、搜索页、详情页这类接口驱动页面。
2. 需要复杂业务状态管理的页面。
3. 需要后台动态配置的模块页。

---

## 3. 第一原则

### 3.1 严格参照原页面

重构时必须以原页面为准，优先级高于“设计优化”。

必须遵守：

1. 区块顺序不能变。
2. 主体布局尺寸不能随意改。
3. 图片显示方式不能自作主张修改。
4. 标题、描述、卡片、边框、留白、间距尽量贴近原页。
5. 如果原页面是“普通展示”，重构后也不能做成另一套视觉语言。
6. 页面内容结束处必须自然收口，底部、尾部不能残留无意义空白，不能出现明显“没做完”的留白段。
7. 图片渲染区域不能为了铺满而直接拉伸图片，优先通过容器比例、裁切方式、定位偏移等方式还原原页面效果。

禁止行为：

1. 自行增加卡片感、阴影、毛玻璃、动画、渐变等原页没有的风格。
2. 未经确认就修改模块比例。
3. 未经确认就把图片从“铺满”改成“完整显示”或相反。
4. 因为代码更好写，就把原布局改成另一种布局。

一句话原则：

**先还原，再重构，不允许借重构名义改版。**

### 3.2 每次都必须有对照基准

每个页面重构前，必须明确两类地址：

1. 原始参考页 URL
2. 本地重构页 URL

示例：

1. 原页面：`http://127.0.0.1:8787/网站开发.html`
2. 重构页：`http://127.0.0.1:8787/网站开发/`

后续验收时，必须始终对照这两个地址。

## 4. 文件组织规范

### 4.0 当前统一目录基准

从现在开始，所有自研重构页面统一收口到：

```text
自研页面重构/
```

当前目录清单只保留一级目录：

```text
自研页面重构/
  AI三维/
  AI平台/
  APP开发/
  article/
  category/
  index_new/
  more/
  plugin/
  search/
  vr_init/
  三维-new/
  三维系列/
  人才招聘/
  数字化/
  查看更多(首页)/
  程序开发/
  网站开发/
  联系我们/
  首页VR/
```

后续新增页面，也统一按 `自研页面重构/` 目录继续扩展，便于维护、对照、同步 OSS。

其中 `plugin/` 目录用于存放“跨业务复用的公共能力”，例如：

1. 公共幻灯片
2. 公共轻交互组件
3. 后续确认可复用的展示型插件

原则是：

1. 公共能力放 `plugin/`
2. 业务页面放各自目录
3. 不允许把公共组件继续散落在某个业务目录里让其他页面相对引用

### 4.1 一页一个目录

每个业务展示页单独建目录，例如：

```text
自研页面重构/
  网站开发/
    index.html
    website-dev.css
```

### 4.2 一页一套业务 CSS

业务展示页默认采用：

1. `1 个 HTML`
2. `1 个业务 CSS`
3. `0 个业务 JS` 或 `1 个极少量业务 JS`

如果页面本身没有真实交互，不要硬拆多个 JS 文件。

目录命名建议继续保持“页面中文名目录 + 页面专属 CSS 文件”：

1. `自研页面重构/网站开发/website-dev.css`
2. `自研页面重构/程序开发/program-dev.css`
3. `自研页面重构/APP开发/app-dev.css`
4. `自研页面重构/AI平台/ai-platform.css`
5. `自研页面重构/AI三维/ai-3d.css`
6. `自研页面重构/联系我们/contact-page.css`
7. `自研页面重构/人才招聘/recruitment-page.css`
8. `自研页面重构/数字化/digital-page.css`

这样后期定位和同步资源时最清晰。

### 4.3 禁止把业务逻辑塞回 HTML

禁止以下做法：

1. 在 `index.html` 中写大段 `<style>`
2. 在 `index.html` 中写大段业务 `<script>`
3. 直接复制旧站整包脚本继续用

允许保留的只有：

1. 远程公共资源引入
2. 极少量初始化脚本

## 5. 重构步骤

### 5.0 先判断是否属于“高风险绝对定位页”

如果原页面具备以下特征，必须按“高风险绝对定位页”处理：

1. 原页面由旧建站平台导出，DOM 冗余极多。
2. 首屏大量元素使用写死的 `left/top/width/height`。
3. 文本、蓝条、装饰图、主视觉图是混合绝对定位。
4. 页面看起来像静态展示，但实际视觉关系非常依赖字体、行高、字宽、定位坐标。

典型页面：

1. `AI平台.html`
2. 后续同类“扒过来的”业务展示页

这类页面的原则不是“常规响应式重排”，而是：

**先按原页坐标关系复刻，再做结构清理。**

### 5.1 先判断页面是否真的需要 JS

开始重构前，先判断页面是否只是展示页。

如果页面只是：

1. Banner 展示
2. 图文区块
3. 案例列表
4. 优势模块

则优先做成纯 `HTML + CSS`。

只有以下情况才加业务 JS：

1. 真正存在切换、过滤、分页、弹窗、异步加载
2. 旧页面确实依赖必要交互

### 5.2 从结构开始，不先做“美化”

建议顺序：

1. 先搭页面结构
2. 再还原区块宽度、高度、间距
3. 再处理图片显示方式
4. 最后才处理小样式细节

不要一开始就加视觉效果。

对于高风险绝对定位页，推荐顺序进一步细化为：

1. 先抽出原页的主区块结构。
2. 先把首屏主视觉单独还原。
3. 首屏对齐后，再做下方案例区、列表区。
4. 最后再处理嵌入 WP 的兼容和样式防覆盖。

禁止一上来就把整页全部“语义化重排”后再慢慢调，因为返工成本会很高。

### 5.3 图片显示必须按原页面逐块校准

不同模块的图片展示策略可以不同，不能全站统一一个规则。

例如同一个页面里可能同时存在：

1. `object-fit: fill`
2. `object-fit: cover`
3. 宽度铺满，高度自动
4. 局部位移裁切

因此：

1. 每个图片区块都要单独对照原页
2. 必要时允许为少数图片写单独 class
3. 不允许为了省事全部套同一种图片规则
4. 除非原页面本身就是拉伸效果，否则不允许为了填满图片区直接把图片拉伸、压扁或变形
5. “图片不能拉伸”不等于所有图片都必须 `max-width: 100%` 或“完整显示”，必须先判断原页到底是完整显示、等比裁切铺满、定位偏移裁切，还是原页本身就有拉伸
6. 对于固定高度的图片区，如果原页是“宽度超出容器后再裁切”，则重构时应允许图片宽度大于容器，并通过 `overflow: hidden`、定位偏移等方式还原，不能因为通用响应式规则把图片压回容器宽度
7. 像页面级 `img { max-width: 100%; }` 这类安全规则，如果会破坏某些图片区的原始裁切方式，必须对该模块单独覆盖，不能为了通用规则牺牲原页还原

### 5.4 对旧脚本的处理原则

旧站里常见的建站平台遗留 JS，默认处理方式如下：

1. 没有实际业务价值的，直接删除
2. 仅为旧平台运行服务的，直接删除
3. 页面无交互依赖的，直接删除
4. 公共悬浮侧边栏这类统一能力，改成远程公共引入

重构页目标不是“兼容旧代码继续跑”，而是“留下必要能力，去掉历史包袱”。

### 5.5 高风险绝对定位页的首屏还原规则

对于类似 `AI平台` 这种首屏由主图、说明条、标题、装饰图混排的页面，必须遵守以下规则：

1. 首屏先固定一个原始设计宽度，例如原页是 `1500px`，就先按 `1500px` 还原。
2. 主视觉容器优先用 `position: relative`，内部元素用绝对定位复刻原页关系。
3. 左右说明条、标题、装饰图、手机图不要急着改成普通流式布局。
4. 原页标题如果本质上只是普通单行文本，不要为了“居中方便”改成 `flex` 垂直居中。
5. 原页文本如果依赖特定字体渲染，必须优先复用原页字体或接近字体；不能默认换成新的字体栈。
6. `line-height`、`font-family`、`font-size`、`font-weight` 一旦变化，视觉位置就可能整体漂移，必须单独校准。
7. 如果原页文字是靠 `top` 坐标摆出来的，就不要再叠加多余的 `transform`、`flex align-items`、`padding` 去二次修正。

一句话：

**首屏文字位置优先靠原页坐标还原，不靠“现代布局技巧”猜。**

### 5.6 原页对照方式必须固定

后续所有同类页面，必须同时保留以下两个对照地址：

1. 原始页：如 `http://127.0.0.1:8787/AI平台.html`
2. 重构页：如 `http://127.0.0.1:8787/AI平台/`

验收时至少对照以下内容：

1. 首屏背景高度是否一致
2. 主标题位置是否一致
3. 左右文案条是否压进主图
4. 图片是否被拉伸
5. 首屏结束后是否出现无意义留白
6. 底部是否自然收口

如果发现“字跑到图片中间”“蓝条压住主图”“图片裁切和原页不一致”，优先回查：

1. 字体是否变了
2. 行高是否变了
3. 是否误用了 `flex`
4. 是否被通用 `img` / `p` / `h` 样式影响
5. 是否因为缩放方案导致坐标关系变化

### 5.7 这类页面最容易踩的坑

后续重构时，默认优先排查以下风险：

1. 原页是旧平台导出页，实际依赖旧字体和旧运行时环境，重构后字宽字高会变化。
2. 页面首屏是“图片 + 文案 + 装饰条 + 标题”的混排，任何一个 `line-height` 变化都会导致文字漂移。
3. 页面级安全规则如 `img { max-width: 100%; }` 可能会破坏原页裁切方式。
4. 本地看着正常，不代表嵌进 WordPress 后也正常；主题全局样式、经典编辑器、页面外链 CSS 都可能覆盖。
5. 原页如果本身是绝对定位，强行改成普通栅格/流式布局，通常会导致首屏不再像原页。

### 5.8 高风险页面的最终交付原则

这类页面允许“结构干净，但视觉还原优先”，具体执行如下：

1. 可以删除旧站冗余 JS、旧运行时、无业务意义代码。
2. 可以把 HTML 结构清理干净。
3. 但不能为了代码整洁牺牲首屏位置、比例和视觉关系。
4. 页面完成后，必须再做一轮 WordPress 嵌入风险检查。
5. 嵌入版需要去掉 `html/head/body`，只保留页面主体和外链资源。
6. 嵌入前必须检查是否存在高风险全局选择器，避免污染主题，也避免被主题污染。

## 6. CSS 约束

### 6.1 必须做页面级作用域隔离

所有业务 CSS 必须收口到页面根容器下。

示例：

```html
<main class="zr-webdev-page">
  ...
</main>
```

```css
.zr-webdev-page {
  color: #111;
}

.zr-webdev-page img {
  display: block;
}
```

### 6.2 禁止的全局选择器

嵌入 WP 前，必须检查并移除以下高风险全局规则：

1. `:root`
2. `*`
3. `html`
4. `body`
5. `img`
6. `a`
7. `p`
8. `h1 ~ h6`

如果确实需要使用，必须改成页面容器作用域版本，例如：

1. `.zr-webdev-page`
2. `.zr-webdev-page *`
3. `.zr-webdev-page img`

### 6.3 命名规范

业务页 class 建议统一加页面前缀，例如：

1. `zr-webdev-*`
2. `zr-ai-*`
3. `zr-appdev-*`

这样嵌入 WP 后，冲突风险最低。

## 7. 公共能力接入规范

### 7.1 统一侧边栏

业务展示页如果需要接入统一侧边栏，按现有站点公共资源引入，不再每页内联维护一套旧代码。

当前统一资源：

1. 基础样式：`https://static.ysjianzhan.cn/website/plugin/sidebar/css/sidebar.css?v=16860282`
2. 主题样式：`https://static.jsss999.com/upload/zrsite/slider/category-sidebar-v1.css`
3. 统一脚本：`https://static.jsss999.com/upload/zrsite/slider/category-sidebar-v1.js`

原则：

1. 页面里只保留远程引入
2. 不重复内联旧版 sidebar 代码
3. 侧边栏逻辑统一在 OSS 维护

### 7.2 页头、页脚、百度统计等公共能力

公共能力优先全站统一处理，不放在单页业务 CSS/JS 里重复维护。

单页只处理：

1. 该页自己的主体结构
2. 该页自己的业务样式

### 7.3 幻灯片公共能力规范

从当前版本开始，业务展示页中凡是“顶部 Banner 幻灯片”这类能力，统一按公共插件处理，不再每个页面各写一套。

当前统一位置：

```text
自研页面重构/
  plugin/
    shared-slider.css
    shared-slider.js
```

#### 7.3.1 组件与配置的边界

必须遵守以下边界：

1. 幻灯片组件是公共能力，只维护一套。
2. 幻灯片图片、文案、张数属于业务配置，必须放在各业务自己的 JSON 里。
3. 公共组件内部禁止写死某个业务的图片 URL。
4. 公共组件内部禁止写死“查看更多”或“首页VR”这类业务语义。
5. 页面是否启用幻灯片、幻灯片有几张图、图的 URL 是什么，都由业务配置决定。

一句话：

**组件统一，配置独立。**

#### 7.3.2 业务页接入方式

业务页接入幻灯片时，按以下方式执行：

1. 页面引入公共 CSS：`../plugin/shared-slider.css`
2. 页面业务 JS 引入公共组件：`../plugin/shared-slider.js`
3. 页面自己的 JSON 提供 `slider` 配置
4. 页面业务 JS 只负责读取本页配置并调用公共组件

禁止以下做法：

1. 把公共幻灯片组件复制到某个业务目录再改一份
2. 让“查看更多”目录充当其他业务页的组件源目录
3. 因为图片不一样就复制一整套组件

#### 7.3.3 JSON 配置要求

幻灯片相关配置必须保留在业务自己的 JSON 中，推荐结构如下：

```json
{
  "slider": {
    "interval": 3000,
    "effect": "all",
    "slides": [
      {
        "imageUrl": "https://xxx/slide-1.jpg",
        "alt": "轮播图一"
      },
      {
        "imageUrl": "https://xxx/slide-2.jpg",
        "alt": "轮播图二"
      }
    ]
  }
}
```

说明：

1. `interval` 表示自动播放间隔
2. `effect` 表示切换动效策略
3. `slides` 为业务自己的图片列表
4. `imageUrl` 必须由业务自己维护
5. `alt` 必须跟业务语义对应

如果某个页面本身只有一个总配置 JSON，也允许把 `slider` 合并进这一份 JSON，不必额外拆文件。

#### 7.3.4 交互还原要求

公共幻灯片组件的交互要求，必须和原页面保持一致，不允许随意删减。

当前统一要求：

1. 支持自动播放
2. 支持左右箭头切换
3. 支持底部圆点分页
4. 圆点必须支持点击切换
5. 当前激活圆点按首页基准处理为红色实心态
6. 非激活圆点保持弱化显示

其中底部圆点交互，当前以：

1. `index_new/home.html`

为统一参照基准。后续如果没有新的明确要求，其他业务页幻灯片分页交互也按这个基准执行。

#### 7.3.5 样式职责划分

幻灯片样式拆分时，按以下职责划分：

公共插件 CSS 负责：

1. 幻灯片基础结构
2. 切换动效基础样式
3. 分页圆点基础样式
4. 分页激活态基础样式

业务页自己的 CSS 负责：

1. 幻灯片容器宽高
2. 箭头尺寸与皮肤图
3. 与当前页面相关的定位微调
4. 仅属于该页的视觉差异

这意味着：

1. 箭头图标资源可以因业务不同而不同
2. 幻灯片图片列表必须因业务不同而不同
3. 但切换机制、分页机制、基础 DOM 结构仍然只维护一套

#### 7.3.6 OSS 同步要求

幻灯片公共能力后续会同步到 OSS，因此必须提前按可远程维护方式组织。

必须满足：

1. 公共组件文件路径稳定
2. 公共 CSS/JS 可以独立同步
3. 业务 JSON 可以独立同步
4. 页面最终只做“引入公共组件 + 读取业务配置”

最终目标不是“本地能跑就行”，而是：

**同步到 OSS 后，公共组件改一处，多个业务页都能复用；业务只需要替换自己的图片配置。**

## 8. WordPress 嵌入规范

### 8.1 嵌入策略

业务展示页最终产物要支持嵌入 WordPress。

建议方式：

1. HTML 页面主体作为嵌入内容
2. CSS、JS、图片走 OSS 绝对地址
3. WP 页面只作为承载容器

### 8.2 嵌入前必须检查

1. CSS 是否存在全局污染
2. 页面最外层容器是否保留
3. 业务资源是否都已换成 OSS 地址
4. 是否误依赖本地相对路径
5. WordPress 是否对嵌入片段自动插入了空 `p`、`br`、包裹段落

### 8.2.1 WordPress 自动节点兜底

业务展示页嵌入 WordPress 后，常见问题不是业务代码本身，而是编辑器或 `wpautop` 自动插入节点，例如：

1. 空 `<p></p>`
2. 片段尾部多一个 `<br>`
3. 图片、绝对定位元素被包进段落
4. 片段前后被额外段落撑开

这些节点会直接导致：

1. 顶部出现白缝
2. 页面尾部出现多余留白
3. 模块中间间距异常
4. 绝对定位元素表现异常

因此嵌入版 CSS 必须允许增加只命中当前页面容器的兜底规则，例如：

```css
.zr-webdev-page p:empty {
  display: none !important;
  margin: 0 !important;
}

.zr-webdev-page + br {
  display: none !important;
}
```

原则：

1. 兜底规则必须带页面前缀
2. 只处理当前业务页，不污染全站
3. 发现 WordPress 自动插入节点时，优先做页面级兜底，不回避问题

### 8.3 经典编辑器注意事项

如果使用经典编辑器：

1. 尽量避免在“可视化”和“源码”之间反复切换
2. 复杂业务 HTML 容易被编辑器改写
3. 更适合使用 Gutenberg 自定义 HTML 或保持代码块原样

原则：

**复杂自研页面不要指望经典编辑器稳定维护。**

## 9. 验收流程

### 9.1 本地验收

每次重构完成后，必须至少做以下对照：

1. 原页面 vs 重构页面并排查看
2. 首屏视觉对照
3. 中间模块对照
4. 图片裁切方式对照
5. 边框、圆角、间距、留白对照
6. 页面底部和尾部是否存在异常留白对照

### 9.2 必查项

1. 区块顺序是否一致
2. 模块宽度是否一致
3. 标题字号和留白是否跑偏
4. 图片是否拉伸、压扁、露白边
5. 是否引入了原页没有的阴影、浮层、动效
6. 页面底部、尾部是否存在无意义大段空白
7. 侧边栏是否正常
8. 控制台是否有报错
9. 嵌入 WordPress 后是否被自动插入空 `p` / `br`

### 9.3 Playwright 对照要求

建议每次都通过浏览器实际查看：

1. 原页面 URL
2. 重构页面 URL
3. 必要时截图对照

不能只看代码判断“应该差不多”。

## 10. OSS 发布规范

### 10.1 发布方式

静态资源同步到 OSS 后，页面内引用全部改为绝对地址。

例如：

```html
<link rel="stylesheet" href="https://static.jsss999.com/upload/zrsite/web/website-dev.css?v=20260317-1" />
```

### 10.2 版本号规则

OSS 有缓存，更新文件后必须带版本号。

例如：

1. `?v=20260317-1`
2. `?v=20260317-2`

### 10.3 发布前检查

1. HTML 中是否仍残留本地路径
2. CSS 中图片地址是否已切 OSS
3. 远程 CSS/JS 是否能直接访问
4. 发布后线上页面是否加载到最新版本

## 11. 当前示例：网站开发页

当前已完成的参考案例：

1. 原页面：`/mnt/d/python_work/image-harvester/html/网站开发.html`
2. 重构目录：`/mnt/d/python_work/image-harvester/html/网站开发/`
3. 页面结构：`index.html`
4. 业务样式：`website-dev.css`

本页重构过程中确认的有效原则：

1. 页面本身无需业务 JS，可只保留 `HTML + CSS`
2. 图片必须按区块分别校准，不能一个规则覆盖全部模块
3. CSS 必须收口到 `.zr-webdev-page`
4. 侧边栏应直接复用统一远程资源
5. 最终效果必须以原页面视觉为准，不做个人发挥
6. 顶部、底部不能留无意义空白，页面必须自然收口
7. WordPress 嵌入后若自动插入空 `p` / `br`，要用页面级 CSS 兜底消除
8. “防拉伸”的通用图片规则不能误伤原页的裁切铺满模块，必要时必须给特定图片区单独解除限制

## 12. 后续执行要求

后面再重构新的业务展示页时，默认按本规范执行：

1. 先确定原页面参考 URL
2. 先做结构还原，不先做优化
3. 一页一个目录
4. 一页一套业务 CSS
5. 页面级 CSS 作用域隔离
6. 先本地对照通过，再同步 OSS
7. 再嵌入 WP 验收

如果某页要故意偏离原页面，必须先明确说明：

1. 哪个区块要改
2. 为什么改
3. 改动范围有多大

否则默认就是“严格还原重构”。
