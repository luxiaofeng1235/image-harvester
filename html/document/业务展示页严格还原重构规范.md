# 业务展示页严格还原重构规范

## 1. 目标

适用于 `网站开发`、`AI平台`、`程序开发`、`App开发` 等业务展示页的重构。

核心目标只有 4 条：

1. 在视觉结构上尽量还原原页面，不随意改布局、尺寸、比例、留白。
2. 设计原则上页面不能出现无意义留白，尤其是底部、尾部不能出现明显空白段。
3. 在代码结构上做干净拆分，去掉旧站冗余脚本和无关依赖，保证后期可维护。
4. 最终产物支持同步到 OSS，并可嵌入 WordPress 页面使用。

---

## 2. 适用范围

本规范适用于以下类型页面：

1. 主要是静态展示页。
2. 原页面存在大量旧建站平台遗留代码、内联脚本、样式冲突风险。
3. 页面本身交互较少，重点是视觉还原，而不是功能开发。
4. 后期需要嵌入到 WordPress 页面中。

不适用于：

1. 分类页、搜索页、详情页这类接口驱动页面。
2. 需要复杂业务状态管理的页面。
3. 需要后台动态配置的模块页。

---

## 3. 第一原则

### 3.1 严格参照原页面

重构时必须以原页面为准，优先级高于“设计优化”。

必须遵守：

1. 区块顺序不能变。
2. 主体布局尺寸不能随意改。
3. 图片显示方式不能自作主张修改。
4. 标题、描述、卡片、边框、留白、间距尽量贴近原页。
5. 如果原页面是“普通展示”，重构后也不能做成另一套视觉语言。
6. 页面内容结束处必须自然收口，底部、尾部不能残留无意义空白，不能出现明显“没做完”的留白段。
7. 图片渲染区域不能为了铺满而直接拉伸图片，优先通过容器比例、裁切方式、定位偏移等方式还原原页面效果。

禁止行为：

1. 自行增加卡片感、阴影、毛玻璃、动画、渐变等原页没有的风格。
2. 未经确认就修改模块比例。
3. 未经确认就把图片从“铺满”改成“完整显示”或相反。
4. 因为代码更好写，就把原布局改成另一种布局。

一句话原则：

**先还原，再重构，不允许借重构名义改版。**

### 3.2 每次都必须有对照基准

每个页面重构前，必须明确两类地址：

1. 原始参考页 URL
2. 本地重构页 URL

示例：

1. 原页面：`http://127.0.0.1:8787/网站开发.html`
2. 重构页：`http://127.0.0.1:8787/网站开发/`

后续验收时，必须始终对照这两个地址。

## 4. 文件组织规范

### 4.1 一页一个目录

每个业务展示页单独建目录，例如：

```text
网站开发/
  index.html
  website-dev.css
```

### 4.2 一页一套业务 CSS

业务展示页默认采用：

1. `1 个 HTML`
2. `1 个业务 CSS`
3. `0 个业务 JS` 或 `1 个极少量业务 JS`

如果页面本身没有真实交互，不要硬拆多个 JS 文件。

### 4.3 禁止把业务逻辑塞回 HTML

禁止以下做法：

1. 在 `index.html` 中写大段 `<style>`
2. 在 `index.html` 中写大段业务 `<script>`
3. 直接复制旧站整包脚本继续用

允许保留的只有：

1. 远程公共资源引入
2. 极少量初始化脚本

---

## 5. 重构步骤

### 5.1 先判断页面是否真的需要 JS

开始重构前，先判断页面是否只是展示页。

如果页面只是：

1. Banner 展示
2. 图文区块
3. 案例列表
4. 优势模块

则优先做成纯 `HTML + CSS`。

只有以下情况才加业务 JS：

1. 真正存在切换、过滤、分页、弹窗、异步加载
2. 旧页面确实依赖必要交互

### 5.2 从结构开始，不先做“美化”

建议顺序：

1. 先搭页面结构
2. 再还原区块宽度、高度、间距
3. 再处理图片显示方式
4. 最后才处理小样式细节

不要一开始就加视觉效果。

### 5.3 图片显示必须按原页面逐块校准

不同模块的图片展示策略可以不同，不能全站统一一个规则。

例如同一个页面里可能同时存在：

1. `object-fit: fill`
2. `object-fit: cover`
3. 宽度铺满，高度自动
4. 局部位移裁切

因此：

1. 每个图片区块都要单独对照原页
2. 必要时允许为少数图片写单独 class
3. 不允许为了省事全部套同一种图片规则
4. 除非原页面本身就是拉伸效果，否则不允许为了填满图片区直接把图片拉伸、压扁或变形
5. “图片不能拉伸”不等于所有图片都必须 `max-width: 100%` 或“完整显示”，必须先判断原页到底是完整显示、等比裁切铺满、定位偏移裁切，还是原页本身就有拉伸
6. 对于固定高度的图片区，如果原页是“宽度超出容器后再裁切”，则重构时应允许图片宽度大于容器，并通过 `overflow: hidden`、定位偏移等方式还原，不能因为通用响应式规则把图片压回容器宽度
7. 像页面级 `img { max-width: 100%; }` 这类安全规则，如果会破坏某些图片区的原始裁切方式，必须对该模块单独覆盖，不能为了通用规则牺牲原页还原

### 5.4 对旧脚本的处理原则

旧站里常见的建站平台遗留 JS，默认处理方式如下：

1. 没有实际业务价值的，直接删除
2. 仅为旧平台运行服务的，直接删除
3. 页面无交互依赖的，直接删除
4. 公共悬浮侧边栏这类统一能力，改成远程公共引入

重构页目标不是“兼容旧代码继续跑”，而是“留下必要能力，去掉历史包袱”。

## 6. CSS 约束

### 6.1 必须做页面级作用域隔离

所有业务 CSS 必须收口到页面根容器下。

示例：

```html
<main class="zr-webdev-page">
  ...
</main>
```

```css
.zr-webdev-page {
  color: #111;
}

.zr-webdev-page img {
  display: block;
}
```

### 6.2 禁止的全局选择器

嵌入 WP 前，必须检查并移除以下高风险全局规则：

1. `:root`
2. `*`
3. `html`
4. `body`
5. `img`
6. `a`
7. `p`
8. `h1 ~ h6`

如果确实需要使用，必须改成页面容器作用域版本，例如：

1. `.zr-webdev-page`
2. `.zr-webdev-page *`
3. `.zr-webdev-page img`

### 6.3 命名规范

业务页 class 建议统一加页面前缀，例如：

1. `zr-webdev-*`
2. `zr-ai-*`
3. `zr-appdev-*`

这样嵌入 WP 后，冲突风险最低。

## 7. 公共能力接入规范

### 7.1 统一侧边栏

业务展示页如果需要接入统一侧边栏，按现有站点公共资源引入，不再每页内联维护一套旧代码。

当前统一资源：

1. 基础样式：`https://static.ysjianzhan.cn/website/plugin/sidebar/css/sidebar.css?v=16860282`
2. 主题样式：`https://static.jsss999.com/upload/zrsite/slider/category-sidebar-v1.css`
3. 统一脚本：`https://static.jsss999.com/upload/zrsite/slider/category-sidebar-v1.js`

原则：

1. 页面里只保留远程引入
2. 不重复内联旧版 sidebar 代码
3. 侧边栏逻辑统一在 OSS 维护

### 7.2 页头、页脚、百度统计等公共能力

公共能力优先全站统一处理，不放在单页业务 CSS/JS 里重复维护。

单页只处理：

1. 该页自己的主体结构
2. 该页自己的业务样式

## 8. WordPress 嵌入规范

### 8.1 嵌入策略

业务展示页最终产物要支持嵌入 WordPress。

建议方式：

1. HTML 页面主体作为嵌入内容
2. CSS、JS、图片走 OSS 绝对地址
3. WP 页面只作为承载容器

### 8.2 嵌入前必须检查

1. CSS 是否存在全局污染
2. 页面最外层容器是否保留
3. 业务资源是否都已换成 OSS 地址
4. 是否误依赖本地相对路径
5. WordPress 是否对嵌入片段自动插入了空 `p`、`br`、包裹段落

### 8.2.1 WordPress 自动节点兜底

业务展示页嵌入 WordPress 后，常见问题不是业务代码本身，而是编辑器或 `wpautop` 自动插入节点，例如：

1. 空 `<p></p>`
2. 片段尾部多一个 `<br>`
3. 图片、绝对定位元素被包进段落
4. 片段前后被额外段落撑开

这些节点会直接导致：

1. 顶部出现白缝
2. 页面尾部出现多余留白
3. 模块中间间距异常
4. 绝对定位元素表现异常

因此嵌入版 CSS 必须允许增加只命中当前页面容器的兜底规则，例如：

```css
.zr-webdev-page p:empty {
  display: none !important;
  margin: 0 !important;
}

.zr-webdev-page + br {
  display: none !important;
}
```

原则：

1. 兜底规则必须带页面前缀
2. 只处理当前业务页，不污染全站
3. 发现 WordPress 自动插入节点时，优先做页面级兜底，不回避问题

### 8.3 经典编辑器注意事项

如果使用经典编辑器：

1. 尽量避免在“可视化”和“源码”之间反复切换
2. 复杂业务 HTML 容易被编辑器改写
3. 更适合使用 Gutenberg 自定义 HTML 或保持代码块原样

原则：

**复杂自研页面不要指望经典编辑器稳定维护。**

## 9. 验收流程

### 9.1 本地验收

每次重构完成后，必须至少做以下对照：

1. 原页面 vs 重构页面并排查看
2. 首屏视觉对照
3. 中间模块对照
4. 图片裁切方式对照
5. 边框、圆角、间距、留白对照
6. 页面底部和尾部是否存在异常留白对照

### 9.2 必查项

1. 区块顺序是否一致
2. 模块宽度是否一致
3. 标题字号和留白是否跑偏
4. 图片是否拉伸、压扁、露白边
5. 是否引入了原页没有的阴影、浮层、动效
6. 页面底部、尾部是否存在无意义大段空白
7. 侧边栏是否正常
8. 控制台是否有报错
9. 嵌入 WordPress 后是否被自动插入空 `p` / `br`

### 9.3 Playwright 对照要求

建议每次都通过浏览器实际查看：

1. 原页面 URL
2. 重构页面 URL
3. 必要时截图对照

不能只看代码判断“应该差不多”。

## 10. OSS 发布规范

### 10.1 发布方式

静态资源同步到 OSS 后，页面内引用全部改为绝对地址。

例如：

```html
<link rel="stylesheet" href="https://static.jsss999.com/upload/zrsite/web/website-dev.css?v=20260317-1" />
```

### 10.2 版本号规则

OSS 有缓存，更新文件后必须带版本号。

例如：

1. `?v=20260317-1`
2. `?v=20260317-2`

### 10.3 发布前检查

1. HTML 中是否仍残留本地路径
2. CSS 中图片地址是否已切 OSS
3. 远程 CSS/JS 是否能直接访问
4. 发布后线上页面是否加载到最新版本

## 11. 当前示例：网站开发页

当前已完成的参考案例：

1. 原页面：`/mnt/d/python_work/image-harvester/html/网站开发.html`
2. 重构目录：`/mnt/d/python_work/image-harvester/html/网站开发/`
3. 页面结构：`index.html`
4. 业务样式：`website-dev.css`

本页重构过程中确认的有效原则：

1. 页面本身无需业务 JS，可只保留 `HTML + CSS`
2. 图片必须按区块分别校准，不能一个规则覆盖全部模块
3. CSS 必须收口到 `.zr-webdev-page`
4. 侧边栏应直接复用统一远程资源
5. 最终效果必须以原页面视觉为准，不做个人发挥
6. 顶部、底部不能留无意义空白，页面必须自然收口
7. WordPress 嵌入后若自动插入空 `p` / `br`，要用页面级 CSS 兜底消除
8. “防拉伸”的通用图片规则不能误伤原页的裁切铺满模块，必要时必须给特定图片区单独解除限制

## 12. 后续执行要求

后面再重构新的业务展示页时，默认按本规范执行：

1. 先确定原页面参考 URL
2. 先做结构还原，不先做优化
3. 一页一个目录
4. 一页一套业务 CSS
5. 页面级 CSS 作用域隔离
6. 先本地对照通过，再同步 OSS
7. 再嵌入 WP 验收

如果某页要故意偏离原页面，必须先明确说明：

1. 哪个区块要改
2. 为什么改
3. 改动范围有多大

否则默认就是“严格还原重构”。
