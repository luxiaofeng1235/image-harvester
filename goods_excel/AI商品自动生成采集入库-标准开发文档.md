# AI商品自动生成采集入库-标准开发文档

## 1. 文档信息
- 文档版本: `v1.27`
- 创建日期: `2026-03-04`
- 更新日期: `2026-03-23`
- 适用项目: `image-harvester/goods_excel`
- 目标系统: `jiujie_shop.jj_wangyi_goods`

## 2. 背景与目标
当前历史采集数据规模有限、颗粒度不足。目标是建设一套可持续运行的数据生产程序，按分类自动生成更细化的商品数据，并自动补齐图片后落库。

补充说明:
- 目标表 `jj_wangyi_goods` 中已存在一部分历史商品数据，后续新增生成任务必须尽量避开与库内历史数据重复或高度相似的商品。

核心目标:
- 支持按 `category_id + 关键词 + 数量` 生成商品。
- 使用千问模型生成结构化商品文案与价格。
- 使用图片搜索结果抓取图片并映射主图/详情图。
- 落地到 MySQL 表 `jj_wangyi_goods`。
- 所有批次标记统一维护在 `jj_wangyi_goods` 单表中，不做按天分表，也不新增批次日志表。
- 结果可控: 价格区间、地域覆盖、批次去重、库内去重、合规校验。

## 3. 范围与非范围
### 3.1 范围内
- AI 结构化商品数据生成。
- 图片搜索抓取与商品图映射。
- 数据校验、重试、入库。
- 可选 Excel 导出与审稿模式。

### 3.2 范围外
- 前台商城 UI 改造。
- 商品上架审核工作流系统化开发。
- 支付、库存、订单模块。

## 4. 业务约束
### 4.1 分类映射

|---|---|---|
| 126 | 苏州特产 | 低中客单为主，强调苏州本地特产与礼赠 |
| 127 | 农副产品 | 以可食用农副产品、农副加工品为主 |
| 128 | 苏超纪念品 | 文创周边，严控高价 |
| 129 | 工艺产品 | 工艺与材质属性并重，允许中高客单 |

### 4.2 本地化要求
- 默认全部商品都与江苏本土文化/产业相关。
- 生成批次尽量覆盖江苏 13 市:
  - 南京、无锡、徐州、常州、苏州、南通、连云港、淮安、盐城、扬州、镇江、泰州、宿迁。

- 126 苏州特产: 建议 `19.90 ~ 399.00`，少量高端礼盒可到 `899.00`。
- 127 农副产品: 建议 `9.90 ~ 299.00`，少量礼盒或高规格干货可到 `699.00`。

- 129 工艺产品: 建议 `39.00 ~ 699.00`，少量收藏或定制款可到 `1999.00`。

## 6. 外部接口定义
### 6.1 千问接口
- URL: `https://dashscope.aliyuncs.com/compatible-mode/v1/chat/completions`
- 方法: `POST`
- 鉴权: `Authorization: Bearer ${QW_KEY}`
- 模型策略:
  - 默认主模型: `qwen-plus` (主生产模型，适用于绝大多数批量商品生成任务)
  - 回退/增强模型: `qwen-max` (复杂生成、失败修复、重点重写)

推荐使用原则:
- 本项目默认采用“`qwen-plus` 主跑 + `qwen-max` 补刀”的组合策略，不建议全量默认使用 `qwen-max`。
- `126 江苏特产`、`127 农副产品`、`128 苏超纪念品` 默认优先使用 `qwen-plus`。
- `129 工艺产品` 默认使用 `qwen-plus`，高工艺、高客单、收藏级或重礼赠商品可切换 `qwen-max` 重写。
- 若 `qwen-plus` 输出连续出现 JSON 不稳、分类跑偏、标题质量弱、交付描述空泛等问题，可对失败候选切换 `qwen-max` 二次生成。
- 目标是让 `qwen-plus` 承担大部分吞吐和成本控制，`qwen-max` 仅处理高复杂度或高风险样本。

请求最小结构:
```json
{
  "model": "qwen-plus",
  "messages": [
    {"role": "system", "content": "系统提示词"},
    {"role": "user", "content": "任务提示词"}
  ],
  "temperature": 0.7
}
```

### 6.2 图片来源说明
- 当前主流程不再使用 `ptapi.jsss999.com/api/fetch/getImages` 这类封装图片接口。
- 当前主流程正式图片来源默认只保留百度图片搜索。
- Bing 图片抓取实现与验证脚本仍保留，但主流程默认关闭；如后续需要恢复补图，可通过 `IMG_ENABLE_BING=1` 重新启用。

### 6.3 Bing 图片搜索抓取
- URL: `https://cn.bing.com/images/search?q=<关键词>&qft=+filterui:imagesize-large&form=IRFLTR&first=1`
- 方法: `GET`
- 抓取策略:
  - 当前实现默认优先使用 Playwright 打开 Bing 页面，等待浏览器完成首屏渲染后，再按卡片容器 `.imgpt` 中包含 `.img_cont.hoff` 的顺序截取图片。
  - 每个卡片优先从 `a.iusc[m]` 的 `m` JSON 字段提取原图地址 `murl`、缩略图地址 `turl`、来源页 `purl`、标题 `t`、描述 `desc`。
  - 若某张卡片未取到 `murl`，可回退详情链接 `view=detailV2` 中的 `mediaurl`；仍失败时才回退卡片缩略图。
  - 搜图关键词固定只使用 `生成后的商品标题(title)`，不再回退 `image_keywords` 或任务关键词。
  - 默认优先抓取大尺寸图片候选，并继续做图片有效性校验。
  - 对 Bing 返回结果增加显式文本过滤，默认剔除明显军事、演习、武器等离题图片结果。
- 说明:
  - 该来源作为图片抓取的主来源，比视频封面更适合商品主图场景。
  - 历史问题根因: 早期使用 `requests + lxml` 直接解析静态 HTML 时，源码中的 `a.iusc[m]` 顺序与浏览器首屏可见顺序可能不一致，因此会出现“页面第一张图不是程序第一张图”的错位。
  - 当前修复后的目标是“以浏览器首屏顺序为准”，也就是用户在 Bing 图片搜索页默认看到的前几张图，与程序抓到的前几张图保持一致。
  - 若运行环境缺少 Playwright 或 Chromium，代码仍会回退到静态 HTML 解析；但要保证和浏览器首屏顺序一致，生产和排查环境都应安装 Playwright 及 Chromium。
  - 若 Bing 图片搜索未返回有效原图，则当前不再回退到第三方封装图片接口。

### 6.4 百度图片搜索抓取
- URL: `https://image.baidu.com/search/index?tn=baiduimage&fm=result&ie=utf-8&word=<关键词>`
- 方法: `GET`
- 抓取策略:
  - 当前实现使用 Playwright 打开百度图片搜索页，等待浏览器完成首屏渲染后，直接按首屏卡片 DOM 顺序提取图片。
  - 每个卡片优先读取 `detail` 链接中的 `objurl` 作为原图地址、`fromurl` 作为来源页，并保留卡片缩略图地址。
  - 搜图关键词固定只使用 `生成后的商品标题(title)`，不再回退 `image_keywords` 或任务关键词。
  - 当前主流程默认只使用百度来源；若后续打开 `IMG_ENABLE_BING=1`，再继续使用 Bing 作为补图来源。
  - 对明显 AIGC/预览类图片继续复用 URL 黑名单过滤，例如 `miaobi-lite`、`creative_center_task`、`feed/dump` 等路径。
- 说明:
  - 百度图片静态 HTML 基本只返回前端壳页面，无法稳定直接解析首屏结果，因此当前实现不走 `requests + HTML` 解析。
  - 当前目标同样是“以浏览器首屏顺序为准”，也就是用户默认看到的前几张图，与程序抓到的前几张图保持一致。

### 6.5 CLIP 图片重排
- 作用位置: `图片抓取完成 -> URL 有效性校验完成 -> 主图/详情图映射前`
- 当前实现文件:
  - `ai_goods_pipeline/clients/clip_image_reranker.py`
  - `ai_goods_pipeline/eval_clip_rerank.py`
  - `ai_goods_pipeline/enums/image_semantics.py`
- 默认状态: 关闭，需通过 `.env` 显式开启 `IMG_ENABLE_CLIP_RERANK=1`
- 当前建议适用分类: `128 苏超纪念品`、`129 工艺产品`
- 当前默认模型目录: `ai_goods_pipeline/runtime/models/chinese-clip-vit-base-patch16`
- 工作方式:
  - 当前会先对“已通过过滤和 URL 有效性校验的静态候选”做一轮缩略图预排，再对前排候选补做原图精排。
  - 不新增搜图来源，不替代百度抓图，不绕过前置过滤。
  - 当静态候选图少于 `2` 张、依赖缺失、模型不可用或分类未命中 `IMG_CLIP_CATEGORY_IDS` 时，自动跳过，不阻塞主流程。
  - 当前只允许从本地模型目录加载，不再回退远端下载；模型目录不存在时直接报本地缺失并跳过。
- 当前边界:
  - `CLIP` 只能在已有候选池内排序，无法解决“候选池本身没有正确商品图”的问题。
  - 现阶段更适合处理 `128/129` 这类“候选池里有对图，但顺序容易被人物图/风景图/泛场景图带偏”的问题。

## 7. 数据契约与字段映射
### 7.1 AI输出契约(JSON数组)
为保证稳定解析，AI 端默认输出固定结构，不再采用宽松多态字段:
- `title` (string，必填，非空)
- `subtitle` (string，必填，非空)
- `price` (number，必填，正数，最多两位小数)
- `selling_points` (array[string]，必填，建议 `3 ~ 5` 条)
- `attrs` (object<string, string|number>，必填，默认不接受 array)
- `image_keywords` (array[string]，必填，建议 `1 ~ 3` 个非空关键词)

固定输出要求:
- `selling_points` 中不允许嵌套对象、数组或空字符串。
- `attrs` 的 value 应为标量，禁止再嵌套对象或数组。
- `image_keywords` 去重后至少保留 `1` 个有效词，不允许返回空数组。
- 除明确扩展字段外，默认禁止输出 schema 外字段，避免模型自由发散。

### 7.2 数据库映射
目标表: `jiujie_shop.jj_wangyi_goods`

| 目标字段 | 来源 | 规则 |
|---|---|---|
| `goods_name` | `title` | 必填，去重后写入 |
| `sub_title` | `subtitle` | 可为空 |
| `category_id` | 任务入参 | 必填 |
| `image` | 有效主图 URL(同步 OSS 后写入) | 必填，失败则重试/跳过 |
| `price` | `price` | 转 `decimal(10,2)` |
| `description` | 文案+详情图 | HTML 拼接 |
| `en_name` | 可选 | 可留空 |
| `batch_id` | 任务批次号 | 首次入库批次号；支持命令行 `--batch-id`，不传时自动回退到 `run_id` |
| `last_batch_id` | 最近处理批次号 | 首次写入时与 `batch_id` 相同；后续补录或重处理时只更新此字段 |
| `source_type` | 来源类型 | 首次来源标记；当前实际写入 `ai_generate / seed_import / legacy_import` |
| `source_note` | 来源备注 | 记录来源文件、分类、入口等简要说明，便于后续筛查 |
| `create_time` | 系统时间 | 自动写入 |
| `update_time` | 系统时间 | 自动写入 |

单表批次策略补充:
- 所有批次管理统一落在 `jj_wangyi_goods` 表内，不新增批次日志表，也不做按天分表。
- `batch_id` 表示“这条商品第一次进入系统时属于哪个批次”。
- `last_batch_id` 表示“这条商品最近一次被主流程生成、导入或补录处理时属于哪个批次”。
- `source_type` 只记录首次来源，不因后续补图、补描述而反复改写。
- `enrich_seed_goods_from_db.py` 作为补录链路，正式写库时只更新缺失字段和 `last_batch_id`，不覆盖原始 `batch_id/source_type`。

### 7.4 图片映射与降级规则
- 当前主流程调用关系为 `pipeline.py -> ImageClient.resolve_images() -> BaiduImageClient.fetch_images()`；若打开 `IMG_ENABLE_BING=1`，则再追加 `BingImageClient.fetch_images()` 作为补图来源。验证脚本与主流程复用同一套抓取实现，不存在“两套顺序规则”。
- 主图默认取首个通过校验的静态图片 URL，优先 `jpg/jpeg/png/webp`，默认不使用 `gif` 作为主图。
- 详情图固定取去重后的后续 `3` 张有效图片，不再接受少图入库。
- 每条商品必须满足 `1 张主图 + 3 张详情图 = 4 张有效图片` 才允许进入数据库，否则判为图片失败并继续补生成。
- 若存在 `gif` 但没有静态图，`gif` 可作为详情图候选，不建议作为主图；连续重试后仍无静态图则判为图片失败。
- 所有分类当前默认只使用 Python 抓取百度图片搜索原图；如后续打开 `IMG_ENABLE_BING=1`，再追加 Bing 图片搜索原图补齐。
- 图片候选在进入 URL 探测前，会先做一轮“分类感知 + 城市冲突 + 明显错域”过滤，优先剔除例如“苏州特产搜到南京特产图”“工艺产品搜到农副产品图”“苏超纪念品搜到工艺摆件图”这类明显错配结果。
- 若开启 `IMG_ENABLE_CLIP_RERANK=1`，则在“静态候选图通过 URL 有效性校验后”增加一轮 `CLIP` 语义重排；当前推荐仅对 `128/129` 开启。
- `CLIP` 语义词、载体词、材质词和查询屏蔽词当前统一维护在 `ai_goods_pipeline/enums/image_semantics.py`，同步图片客户端、异步图片客户端和 `CLIP` 重排器共用这一份枚举定义。
- 当百度首屏前 `4` 张图都通过校验且未被过滤时，最终结果应表现为“第 `1` 张主图 + 第 `2~4` 张详情图”。
- 若首屏图片存在失效、被显式文本过滤、不是有效图片、重复 URL 等情况，最终主图/详情图会顺延到后续百度候选；若后续重新开启 Bing，则也可能顺延到后续 Bing 候选。因此“首屏顺序一致”与“最终写库四张图完全等于首屏前四张”不是同一个约束层级。
- 所有分类当前都不再使用项目内预置素材兜底，图片不足时直接判为图片失败并继续补生成。
- `128 苏超纪念品` 应优先使用不含官方 logo、球员肖像、受保护视觉元素的通用场景图或自有风格图，避免侵权风险。
- 主图和详情图在写库前应统一同步到 OSS，并使用业务访问域名写入数据库。
- 默认建议开启 OSS 同步；如需排查性能或先验证生成链路，可通过 `OSS_ENABLED=0` 临时关闭，此时数据库直接写入原图 URL。
- 详情图 HTML 必须固定输出 `3` 个有效 `img` 标签，禁止保留模板占位符、空链接或缺图入库。

## 8. Prompt工程标准
### 8.1 组装结构
- `system_prompt`: 全局角色与硬规则
- `category_profile`: 分类个性化规则
- `task_prompt`: 当前任务输入(关键词/数量/城市池)
- `output_schema`: 强制 JSON 字段定义
- `self_check_prompt`: 去重与合规自检
- `history_guard`: 库内历史标题摘要、禁用命名模式、重复提醒

Prompt工程目标:
- 稳定性优先于文案花样，先保证分类正确、价格正确、地域正确、结构正确，再追求表达丰富。
- 每轮建议按目标数量的 `1.2 ~ 1.5` 倍生成候选，再经程序校验、去重、补生成凑满最终数量。
- 同一任务尽量采用小批次生成，例如每批 `10 ~ 20` 条，降低大批量一次生成导致的质量漂移。
- 模型使用遵循“先 `qwen-plus`、后 `qwen-max`”原则，只有候选不达标或商品复杂度明显较高时才升级到 `qwen-max`。

### 8.2 system_prompt 约束
- 角色: 电商商品策划助手。
- 仅输出 JSON，禁止额外说明。
- 禁止输出 Markdown 代码块、标题、注释、解释文字、序号、前后缀说明。
- 禁止输出外链、联系方式、夸大承诺、违规内容。
- 强调江苏本地化语境。
- 标题、副标题、卖点、属性必须可直接用于电商后台，不得输出“示例”“参考”“可按需调整”等占位语。
- 禁止虚构知名品牌联名、官方授权、地理标志认证、疗效功能、保真承诺等无法验证的信息。
- 禁止虚构非遗名录、老字号、传承人、获奖、专利、机构合作、客户案例、上线效果等无法核验的信息；拿不准时必须改用保守描述。
- 如任务已指定 `category_id`，则所有候选商品必须严格服从该分类定位，不得跨类生成。
- 如已提供历史标题黑名单或重复提醒，必须主动避开高相似命名。

### 8.3 分类个性化策略
- 126/129: 强约束价格，禁止夸高。
- 128: 服务型商品可高客单，但必须交付范围明确。
- 127: 工艺和材质信息必须可解释。

### 8.4 高质量输出约束
- `title` 建议 `14 ~ 28` 个中文字符，尽量包含“地域/品类/特色/场景”中的 `2~3` 个维度，不要堆砌泛营销词。
- `subtitle` 建议 `10 ~ 30` 个中文字符，必须补充产地特色、原料特色、工艺特色或适用场景，不得与标题简单重复。
- `selling_points` 建议输出 `3 ~ 5` 条，每条只表达一个清晰卖点，不要同义反复。
- `attrs` 优先输出对象结构，字段值应简洁明确，避免整段营销文案。
- `image_keywords` 必须服务于搜图，优先采用“城市/地域 + 商品名 + 细分词”的组合。
- 单批次商品在城市、细分类、价格带、礼赠场景上要有分散度，不能大量重复同一套路。
- 标题命名应接近真实电商商品，不要大量出现“高端臻选”“匠心尊享”“爆款热卖”等空泛套话。
- 若无法确认某项产地、工艺、认证、背书是否真实存在，必须用可落地的通用表达替代，禁止为了丰富文案而编造。

### 8.5 苏州特产(126)专属提示词约束
定位要求:
- 以苏州本土食品、地方特产、伴手礼、节令礼盒为主。
- 商品应能被普通消费者一眼识别为“苏州相关特产”，不能写成泛江苏或全国通货。
- 低中客单为主，突出苏式风味、送礼属性、节庆走访、企业伴手礼等场景。

优先生成维度:
- 地域维度: 苏州、姑苏、阳澄湖、洞庭山、昆山、太仓、常熟、张家港、吴江。
- 品类维度: 苏式糕点、茶饮茶礼、熟食卤味、蜜饯果脯、酱菜、水产干货、伴手礼礼盒。
- 表达维度: 地域、风味、原料、净含量、包装形式、送礼场景。

禁止生成内容:
- 明显非苏州产地、非苏州文化来源的普通商品冒充苏州特产。
- 全国通用品牌零食、跨省常见快消品、纯进口食品、与苏州无明确关联的通货型商品。
- 与“特产”无关的工艺摆件、茶具香器、服务类商品。
- 只有空泛营销词、看不出苏州地域特色的标题。

126 标题和属性硬约束:
- 标题尽量体现 `苏州地域词 + 核心品类 + 特色/场景`。
- `subtitle` 必须写清地方风味、原料特点、净含量、适用场景中的至少一项。
- `attrs` 至少包含 `产地城市`、`规格`、`包装形式`、`适用场景`，其中 `产地城市` 必须写为 `苏州`。
- `image_keywords` 至少包含一个苏州地域词和一个具体商品名。
- 常规价格应落在 `19.90 ~ 399.00`，高价礼盒必须体现礼盒构成、规格或送礼定位。

126 批次分布建议:
- 单批次优先覆盖苏式糕点、茶礼、熟食、干货、蜜饯等多个品类，不要只集中在一种茶礼盒。
- 礼盒类建议不超过本批次的 `40%`。
- `19.90 ~ 99.00` 为主力价格带，`100 ~ 399` 为补充价带，`399` 以上仅少量高端礼盒可出现。

### 8.6 农副产品(127)专属提示词约束
定位要求:
- 以江苏本地农产品、农副加工品、粮油干货、水产干货、禽肉制品、酱菜调味品为主。
- 商品必须是可食用的农副产品或农副加工品，不能混入工艺礼品、服务商品或纯文创周边。
- 标题应更像真实电商农副品，不要只讲故事，也不要只有礼盒感没有商品形态。

优先生成维度:
- 产地维度: 南京、无锡、徐州、常州、苏州、南通、连云港、淮安、盐城、扬州、镇江、泰州、宿迁。
- 品类维度: 粮油杂粮、菌菇干货、水产干货、禽肉制品、果干蜜饯、酱菜调味品、茶品。
- 表达维度: 产地、原料、规格、包装、储存方式、家庭食用或送礼场景。

禁止生成内容:
- 工艺摆件、服务套餐、纯文创纪念品、纯进口跨境商品。
- 没有明确品类、没有规格、没有包装信息的空泛礼盒。
- 与江苏无明确关联的全国通货型农副商品。

127 标题和属性硬约束:
- 标题尽量体现 `产地 + 品类 + 状态/包装`。
- `subtitle` 必须明确原料、风味、净含量、储存方式中的至少一项。
- `attrs` 至少包含 `产地城市`、`规格`、`包装形式`、`储存方式`。
- `image_keywords` 优先采用“城市名 + 品类名 + 包装/状态词”的组合。
- 常规价格应落在 `9.90 ~ 299.00`，高于 `299` 的商品必须有礼盒化、高规格原料或大包装解释。

127 批次分布建议:
- 单批次尽量覆盖多个江苏城市，不要整批集中在同一城市。
- 不要全部集中在同一种品类，例如全部是茶或全部是酱菜。
- 保持日常食用款与礼盒款的梯度。

### 8.7 苏超纪念品(128)专属提示词约束
定位要求:
- 以江苏足球联赛氛围、城市助威文化、球迷伴手礼、低客单文创纪念品为主。
- 商品应同时具备“江苏城市元素”与“足球/助威/纪念”语义，不能只是普通旅游纪念品。
- 强调便携、好送、低门槛消费、活动现场售卖或线上周边售卖场景。

优先生成维度:
- 载体维度: 冰箱贴、钥匙扣、徽章、贴纸、水杯、帆布袋、毛绒挂件、亚克力摆件、手机支架、挂绳、小旗帜。
- 城市维度: 结合江苏 13 市地标、昵称、配色、地域符号与球迷助威语境。
- 场景维度: 助威应援、观赛打卡、旅行伴手礼、球迷交换礼、活动纪念。

禁止生成内容:
- 暗示官方授权、赛事官方指定、球队官方联名等无权证明的信息。
- 直接使用真实球员姓名、受保护 logo、俱乐部标识、赛事官方视觉资源进行命名。
- 与足球助威无明显关系的普通旅游文创或普通日用品。
- 低于分类价带的异常低价商品，或高价却没有礼盒化、套装化说明的商品。

128 标题和属性硬约束:
- 标题尽量体现 `江苏城市/苏超氛围 + 纪念品载体 + 助威/伴手礼场景`。
- `subtitle` 必须交代材质、手感、便携性、使用场景中的至少一项。
- `attrs` 至少包含 `城市主题`、`材质`、`规格尺寸`、`适用场景`。
- `image_keywords` 至少包含城市名、足球/助威语义和具体载体名。
- 常规价格应落在 `5.90 ~ 99.00`，礼盒类或组合套装可到 `299.00`，不得生成低于 `5.90` 的低价杂货。

128 批次分布建议:
- 单批次尽量覆盖 `8` 个以上城市或多个地域符号，不要只围绕 1~2 个热点城市。
- 单一载体占比建议不超过本批次的 `30%`。
- 保持“小件快消 + 中件礼赠”的结构，不要全部是毛绒或全部是冰箱贴。

### 8.8 工艺产品(129)专属提示词约束
定位要求:
- 以传统工艺、地方手作、器物摆件、工艺礼品、文化创意工艺品为主。
- 商品必须体现“工艺/材质/器型/用途”中的至少两项，不能只剩装饰用途。
- 适合礼赠、赏玩、茶空间、书房陈设、家居装饰等真实消费场景。

优先生成维度:
- 工艺维度: 紫砂、云锦、苏绣、竹编、木作、玉雕、金箔、陶瓷、雕刻、漆器。
- 表达维度: 材质、器型、工艺流派、使用场景、礼赠属性、文化气质。
- 场景维度: 茶席、书房、家居陈设、节庆赠礼、商务礼赠、个人收藏。

禁止生成内容:
- 没有明确工艺出处的普通家居摆件、普通香薰、普通蜡烛、普通饰品冒充工艺产品。
- 虚构“大师监制”“馆藏同款”“官方认证”“孤品绝版”等无法证明的背书。
- 把食品礼盒、苏超周边、服务商品混入工艺产品。
- 只有材质词、没有工艺说明的泛工艺品。

129 标题和属性硬约束:
- 标题尽量体现 `工艺/材质 + 器型/载体 + 使用或礼赠场景`。
- `subtitle` 必须明确材质特点、工艺亮点、用途场景中的至少一项。
- `attrs` 至少包含 `工艺类别`、`核心材质`、`规格尺寸`、`适用场景`。
- `image_keywords` 优先采用“工艺名 + 材质 + 器物名”或“城市名 + 工艺名 + 器物名”的组合。
- 常规价格应落在 `39.00 ~ 699.00`，高于 `699` 的商品必须有收藏级、定制级、贵重材质或复杂工艺解释。

129 批次分布建议:
- 单批次不要大量集中在同一种载体，例如全部是摆件或全部是团扇。
- 中低价礼赠款和中高价工艺款要有梯度，避免全是高价或全是低价。
- 每批至少覆盖 `3` 种以上工艺/材质方向。

### 8.9 self_check_prompt 自检要求
- 逐条检查是否符合指定 `category_id` 的定位、价格区间和禁用项。
- 逐条检查标题是否与历史商品标题重复或高度相似，如相似则直接重写。
- 逐条检查是否具备江苏本地化信息，若地域信息缺失则直接判为不合格。
- 对 `126` 检查是否真为苏州特产，是否误混全国通货、跨城特产或无地域食品。
- 对 `127` 检查是否真为可食用农副产品或农副加工品，是否缺少产地和规格信息。
- 对 `128` 检查是否同时具备城市元素和足球纪念语义，是否存在侵权风险表述。
- 对 `129` 检查是否有明确工艺、材质、器型支撑，是否只是普通摆件或泛装饰品。
- 逐条检查 `attrs` 是否完整、`image_keywords` 是否可用于搜图、价格是否与商品定位匹配。
- 最终只返回通过自检的 JSON 数组，不返回解释过程。

## 9. 校验与容错
### 9.1 强制校验
- 字段完整性校验: 缺核心字段即失败。
- 价格校验: 不在分类范围内则重试。
- 去重校验:
  - 与本批次 title 去重。
  - 默认与库内全表历史商品 `goods_name` 做精确去重，不仅限同分类。
  - 与库内近似标题去重(建议相似度阈值 `>=0.88` 拦截)。
  - 对标题做标准化后再比对，至少包括: 去空格、统一全半角、统一常见标点、大小写归一。
  - 近似匹配建议优先使用 `rapidfuzz.fuzz.ratio`；无第三方依赖时可回退 `difflib.SequenceMatcher.ratio`。
  - 若命中库内重复或高相似商品，则该候选商品直接丢弃并补生成，直到满足目标数量或达到重试上限。
- 地域校验: 批次内城市分布不能过于集中。

补充要求:
- 程序启动时应先拉取目标表已有商品标题，作为本次任务的库内去重基线。
- 数据库当前没有针对 `goods_name` 的唯一索引，不能依赖数据库约束防重，必须在应用层完成去重拦截。
- 默认策略为“宁可少量补生成，也不要写入明显重复的历史商品”。

### 9.2 图片校验
- URL 去重。
- HEAD/GET 可访问且状态码 `200`。
- `Content-Type` 为图片。
- 长度建议 `>1KB`。
- 主图优先过滤 `gif`，除非业务明确允许。
- 同一商品的主图和详情图 URL 不重复计入。
- 应增加图片来源质量过滤，默认剔除明显新闻封面、视频封面、素材站预览图、文章配图等与商品主图不匹配的链接。
- 图片搜索固定只使用完整商品标题，避免 `image_keywords` 或通用关键词把结果带偏。
- 若开启 `CLIP`，其结果只作为候选排序增强，不替代有效性校验，也不放宽 `1 主图 + 3 详情图` 的入库标准。
- 当主流程关闭 Bing 时，Bing 首屏顺序验证只作为独立排查工具保留；最终入库结果仍要经过文本过滤、图片有效性校验和去重，不应把“最终四张图顺序变化”误判为 Bing 抓取顺序错误。

### 9.3 重试策略
- 千问接口: 最多 `3` 次，指数退避 `1s/2s/4s`。
- 图片抓取与图片探测: 最多 `3` 次，指数退避 `1s/2s/4s`。
- 单条商品最大处理次数: `2` 轮，超限入失败队列。
- 任务级总候选处理上限建议为 `count * 3`，至少 `30` 条；超过上限仍未补足数量时，任务按“部分成功”或“失败”收敛，不无限循环。

## 12. 运行方式
示例:
```bash
python3 ai_goods_pipeline/generate_goods.py \
  --category-id 126 \
  --keywords "苏州特产,苏州碧螺春,苏式糕点,阳澄湖伴手礼" \
  --count 50 \
  --model qwen-plus \
  --batch-id suzhou_20260323_a \
  --write-db 1
```

可选参数:
- `--dry-run 1` 仅生成不入库
- `--export-excel 1` 导出审稿文件
- `--city-strategy balanced` 按13市均衡分布
- `--batch-id custom_batch_xxx` 手动指定本次批次号；不传时自动使用系统生成的 `run_id`

参数语义补充:
- `--count` 表示最终通过校验并成功入库或成功导出的商品数量，不是模型一次返回的候选数量。
- 若候选商品因重复、价格越界、图片失效、字段缺失等原因被丢弃，程序应自动继续补生成，直到凑满 `count` 或达到任务级总尝试上限。
- `--dry-run 1` 下也应严格执行去重、图片校验和失败记录，只是不落库。
- `--export-excel 1` 建议导出“通过候选 + 失败原因 + 审稿备注”三类信息，便于人工复审。
- `--batch-id` 仅决定本次任务写入的批次标记，不影响去重、图片抓取和模型生成逻辑。

## 13. 测试与验收
### 13.1 功能验收
- 能按分类稳定生成指定数量商品。

### 13.1.1 Bing 首屏顺序最小闭环验证
- 为避免主流程中的图片校验、回退和映射逻辑干扰顺序判断，Bing 首屏顺序应使用独立验证脚本单独确认。
- 验证脚本: `goods_excel/ai_goods_pipeline/verify_bing_order.py`
- 推荐命令:
```bash
python3 ai_goods_pipeline/verify_bing_order.py --query "利物浦晋级" --count 4
```
- 该脚本只验证 Bing 图片搜索抓取本身，输出当前代码实际使用的搜索 URL，以及首屏前 `N` 张图片的 `title/image_url/thumbnail_url/source_page`。
- 验证时应同时在浏览器打开同一个 URL：
```text
https://cn.bing.com/images/search?q=<关键词>&qft=+filterui:imagesize-large&form=IRFLTR&first=1
```
- 若脚本输出的前 `N` 条与浏览器首屏默认顺序一致，则说明“Bing 抓取顺序层”已正确；后续若主图/详情图不同，再排查图片校验、过滤和回退逻辑。

### 13.1.2 百度首屏顺序最小闭环验证

### 13.1.3 CLIP 重排最小闭环验证
- 为避免把“搜图顺序问题”和“重排增强问题”混在一起，`CLIP` 应单独做候选重排验证。
- 验证脚本: `goods_excel/ai_goods_pipeline/eval_clip_rerank.py`
- 推荐命令:
```bash
python3 ai_goods_pipeline/eval_clip_rerank.py \
  --title '真丝长方丝巾 防晒百搭丝绸配饰' \
  --category-id 129 \
  --query '真丝 长方丝巾 平铺' \
  --count 4 \
  --enable-clip-rerank 1
```
- 该脚本会输出:
  - 当前 `CLIP` 运行状态
  - 本次查询语句
  - 原始候选图片 URL
  - 重排后的 URL 与得分
- 若只是验证整链路是否打通，可直接使用 `dry-run + force-image-refresh` 跑单条种子商品，例如:
```bash
IMG_ENABLE_CLIP_RERANK=1 \

  --category-id 129 \

  --concurrency 1 \

  --dry-run 1
```

## 15. 风险与应对
- 风险: 模型返回非 JSON。
  - 应对: JSON schema 校验 + 自动重试 + 修复器。
- 风险: 价格漂移不合理。
  - 应对: 分类价带硬校验，超限直接拦截。
- 风险: 图片失效。
  - 应对: URL 校验 + 失败重试 + 备用关键词。
- 风险: 密钥泄露。
  - 应对: key 轮换、最小权限、配置隔离。

### 16.4 当前正式链路整理
- 输入层: `generate_goods.py` 接收 `category_id + keywords + count + model + write_db + dry_run`，并从根目录 `.env` 读取数据库、千问、图片与 OSS 配置，目标表为 `jj_wangyi_goods`。
- 批次层: 当前只维护 `jj_wangyi_goods` 单表批次元数据；主生成、种子导入、老 Excel 导入都写入 `batch_id/last_batch_id/source_type/source_note`，支持命令行自定义 `--batch-id`，不传则回退为系统生成 `run_id`。
- 生成层: `pipeline.py` 调用 Prompt 组装逻辑，按 `126 苏州特产 / 127 农副产品 / 128 苏超纪念品 / 129 工艺产品` 四类画像约束生成结构化商品草案，默认主模型为 `qwen-plus`，必要时可切 `qwen-max`。
- 校验层: 生成结果先经过 JSON 结构校验、分类约束、价格区间、字段完整性、标题去重和历史库去重，不合格候选直接丢弃并补生成。
- 图片层: 当前搜图关键词固定只使用生成后的完整 `title`，主流程正式图片来源默认仅为百度图片，按 Playwright 渲染后的首屏 DOM 顺序抓取，不再使用 `ptapi` 封装接口，也不再使用项目内预置素材兜底；如后续打开 `IMG_ENABLE_BING=1`，再启用 Bing 补图。对 `128/129` 可按开关追加 `CLIP` 语义重排，但 `CLIP` 只在已有候选图内排序，不替代搜图本身。
- 映射层: 抓回图片后继续做可访问性、类型、大小、去重和离题过滤，最终固定映射为 `1 张主图 + 3 张详情图`；如开启 OSS，则先上传 OSS 再写业务访问域名。
- 入库层: 只有同时满足文本校验与 `4` 张有效图片的商品才允许写入 `jj_wangyi_goods`，否则记失败并继续补生成，直到达到目标数量或任务级尝试上限。
- 补录层: 新增 `enrich_seed_goods_from_db.py` 作为第二方案，直接查询库内 `image` 或 `description` 为空的存量种子商品，按单商品单 prompt 异步补全文案与图片；当前默认仍只走百度图片，可通过 `--ids` 和 `--limit 1` 做最小闭环验证。
- 验证层: 图片顺序问题已拆成最小闭环验证，`verify_baidu_order.py` 与 `verify_bing_order.py` 只验证抓取顺序本身，主流程联调再负责验证过滤、映射、OSS 与入库表现。
- 运行时层: `generate_goods.py` 新增 `--check-runtime 1`，可在不生成、不入库的情况下快速确认当前图片运行环境，输出百度渲染状态、Bing 是否启用以及对应渲染能力，优先排除环境问题。
